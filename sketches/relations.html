A field, read

A field, read

One whole field, written out as it would stand, in the candidate the simulations pointed to: a holon is an identity, what it is (instance), and a body. Nothing else is stored. References sit inside bodies, written so they can be seen without knowing any type. Part and whole is read from the whole's body: in prose, a link standing alone as a paragraph places a part; elsewhere a type holds an ordered list.

The data is simulated but grounded: the wiki is this wiki, the rest is what such things really hold. Step with ← and →, or j and k.

-- how to read the blocks

store a                          -- a store, and the short name used for it below
brief a:store { … }             -- a holon: its type, then its name in its store
  title  "The store"              -- a value in the body
  about  -> a:store               -- a reference, to the holon's identity
  about  -> a:store @v7           -- a reference pinned to one version
  made   #6ab1043                 -- a commit, named by its hash
  [The formats](-> a:formats)    -- a link in prose; alone in a paragraph it places a part

-- a holon's real identity is an id like 01JB7K…; names are labels, unique in their store
-- the four stores in this field

store g   glass                -- types, components, programs; everyone pulls it, read only
store a   cwejman.dev          -- the author's published store: the wiki, his words, his music
store ah  the author's home     -- his engine's own field: runs, traffic, contacts, his layout
store r   Ana's home            -- a reader who pulled g and a: her notes, her list, her layout

-- the author's engine reads g + a + ah as one field
-- Ana's engine reads g + a + r as one field
-- nobody ever writes into a store they pulled

Types store g

A type is a holon too. It says what keys a body of that type holds, and what each holds. The engine checks a body against it at commit. Types never decide where references are: a reference is visible as one wherever it stands.

type g:type {
  keys   map<text, shape>
}

type g:brief {
  title  text
  prose  prose                   -- markdown; a link alone in a paragraph places a part
}

type g:record {
  title  text
  prose  prose
  of     -> g:type                -- what its entries are
  order  key                     -- which key orders them: entries are found, not listed
}

type g:said {
  record -> g:record              -- the record it is an entry of
  day    date
  prose  prose
}
type g:program {
  title  text
  takes  -> g:type?               -- what its input is
  gives  text                    -- "effect" | "value"
  code   code
}

type g:run {
  program -> g:program @version  -- pinned: the code that actually ran
  input   any
  within  -> g:run?               -- the run that called this one, if any
  at      time
  ended   time?
  result    any?                   -- what it gave back
  commits list<commit>           -- what its effects became
  refused text?
}

type g:visit {
  page     -> any               -- the holon the page drew
  at       time
  browser  text
  system   text
  referrer url?
}
type g:person       { name text,  prose prose? }
type g:organisation { name text,  orgnr text?,  site url? }
type g:role {
  who    -> g:person
  where  -> g:organisation
  title  text
  from   date
  to     date?
}

type g:artist { name text }
type g:track  { title text,  by list<-> g:artist>,  seconds number,  isrc text? }
type g:album  { title text,  by list<-> g:artist>,  year number,
                 tracks list<{ disc number, n number, track -> g:track }> }
type g:playlist { title text,  entries list<{ track -> g:track, added time }> }

type g:note    { about -> any @version,  quote text?,  prose prose }
type g:list    { title text,  items list<{ item -> any, why text? }> }

The wiki store a

Each brief holds its parts in its own prose, each with the sentence that places it. "The store" stands in two places: the architecture places it, and so does the primitives brief, each with a sentence of its own. Nothing on "The store" says where it stands.

brief a:glass {
  title  "Glass"
  prose  """
    Glass puts data, programs, AI and interfaces in one place, as small whole
    pieces kept with their whole history, and runs them with a real engine in
    your own browser. …

    Everything in glass stands on a few primitives, so they come first.

    [The primitives](-> a:primitives)

    Holding the primitives, the architecture says where they are kept and how
    they move …

    [The architecture](-> a:architecture)

    …

    [As it was said](-> a:said)
  """
}
brief a:primitives {
  title  "The primitives"
  prose  """
    Data, types, programs, AI and interfaces are one field of whole pieces …

    ## 3. Store

    A store is where holons are kept and how they travel. How, whole, is told
    in the architecture, and it is read here as well:

    [The store](-> a:store)
    …
  """
}

brief a:architecture {
  title  "The architecture"
  prose  """
    A working application, a site among them, needs state …

    The store comes first, since everything else moves it or reads it.

    [The store](-> a:store)

    The client holds the engine and the interface …

    [The client](-> a:client)
    …
  """
}
brief a:store {
  title  "The store"
  prose  """
    A store is where a field is kept and how it travels: a set of objects that
    never change, each named by what it holds, and one pointer that moves. …

    ## 2.2 A commit says how the field result to be this way

    A commit is one change to the field, whole. … The run is kept in the home
    of whoever ran it, which is often not the store the commit lands in, so
    the link runs from the run to the commit, never back.
    …
    Glass's object model is its own, with only the smallest standards beneath
    it; the background, and why, are in the formats.

    [The formats considered](-> a:formats)
  """
}

-- 31 briefs in all; 34 lone links place them; 41 links inside sentences only mention

Programs store g

Programs are holons holding code. The completion model is one program, each tool another, the harness a third that calls them. None of them holds anything about the runs made of it.

program g:edit {
  title  "Edit"
  gives  "effect"
  tool   "Change a holon's body: what is given replaces, what is left out stays."
  code   """
    export default ({ id, body }) => ({ put: { id, body } })
  """
}

program g:read {
  title  "Read"
  gives  "value"
  tool   "Read one holon, and what stands beneath it."
  code   "export default ({ id }, run) => run.read(id)"
}

program g:complete {
  title  "Complete"
  gives  "value"
  model  "claude-opus-5-5"
  code   """
    import Anthropic from '@anthropic-ai/sdk'
    export default async ({ system, messages, tools }) => { … }
  """
}

program g:harness {
  title  "Harness"
  gives  "value"
  asks   "words"
  code   """
    export default async ({ words }, run) => {
      // ask complete; run the tools it calls as child runs; until it answers
    }
  """
}

A run, and what it changed store ah

The author asked the harness to tighten a brief. The run and every step it took are holons in his home. Each child run says which run called it. The commits are named by hash: they live in store a, the run only records them.

run ah:run-0412 {
  program  -> g:harness @v3
  input    { words "Tighten the face of The store; keep every claim." }
  at       2026-11-02T09:14:03Z
  ended    2026-11-02T09:15:41Z
  result     { said "I shortened the face to two sentences and kept the confidence line." }
  commits  [ #c71e0a2 ]
}

run ah:run-0413 {                      -- turn 1: the model is asked
  program  -> g:complete @v2
  within   -> ah:run-0412
  input    { messages [ … 1 ], tools [ "read", "edit", "note" ] }
  at       2026-11-02T09:14:03Z
  result     { stop "tool_use", calls [ { read { id -> a:store } } ] }
}

run ah:run-0414 {                      -- the tool it called
  program  -> g:read @v1
  within   -> ah:run-0412
  input    { id -> a:store }
  result     { title "The store", prose "A store is where a field is kept …" }
}

run ah:run-0417 {                      -- turn 3: the edit
  program  -> g:edit @v1
  within   -> ah:run-0412
  input    { id -> a:store, body { prose "A store is where a field is kept and how it travels …" } }
  commits  [ #c71e0a2 ]
}

The layout stores g and r

The store ships an entry. Ana's arrangement starts as that entry and becomes hers on her first change. The split tree is a value inside the arrangement's body: resizing a divider is one new version of one holon, and the arrangement's versions are her back and forward.

entry a:entry {
  layers [ { mount { component -> g:reader, reads -> a:glass } },
           { mount { component -> g:overlay } } ]
}

arrangement r:arrangement {
  from   -> a:entry @v2              -- what it started as
  root   { split  { direction "row", ratio 0.62,
             a { mount { component -> g:reader, reads -> a:store } },
             b { split { direction "column", ratio 0.5,
                   a { mount { component -> g:notes, reads -> a:store } },
                   b { mount { component -> g:list,  reads -> r:to-read } } } } } }
}

-- r:arrangement has 23 versions: each one a split, a resize, a mount changed

Components store g

A component says the type it takes. The interface asks the field which components take the type of what is to be drawn, so nothing about drawing is stored on the drawn.

component g:reader {
  takes  -> g:brief
  code   "reader.tsx"             -- the brief whole, then its parts in order, each by its face
}

component g:said-day {
  takes  -> g:said
  code   "said-day.tsx"
}

component g:notes {
  takes  -> any
  code   "notes.tsx"              -- the notes whose about points at what it reads
}

component g:track-row {
  takes  -> g:track
  template { row { cell "$.title", cell "$.by", cell "$.seconds as m:ss" } }
}

read g:component where takes = -> g:brief       -- g:reader

What is not in it

No ownership, no relates, no universal membership, no stored parts. What remains open is said here, not settled.
